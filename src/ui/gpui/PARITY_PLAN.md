# Plan to reach parity with the web UI

[PARITY.md](PARITY.md) lists what is missing. This is the order to close it in, what each step needs first, and how each step is known to be done.

## What "done" means

Every row in PARITY.md is either `present`, or moved to a short list of things this client will not do, each with its reason. PARITY.md is the tracker: a task is not finished until its rows are changed there.

## The size, said plainly

The open rows come to about **190 small, 205 medium and 75 large** items (small is hours, medium is days, large is a week or more of one developer's time). The web client is roughly 90,000 lines; this is a second client of comparable scope, not a round of fixes. The plan is therefore ordered so that every phase ends in something that can be used and seen, and so that stopping after any phase leaves a coherent client.

About half of the open rows cannot be drawn until the engine API offers more. Three foundations are missing under almost everything else: a wider engine surface, a fuller set of view parts (tooltip, toast, slider, popover, keyboard focus), and an application shell (tray, hotkeys, notifications, sounds, logs). Building those first is slower to show results for two phases and much faster after.

## Decisions (answered 2026-11-14)

| # | Decision | Answer |
|---|---|---|
| 1 | How far parity goes | Every member-facing feature to full parity. Administration to full parity too, the heavy editors included. YouTube embeds are wanted: after the rest, find a way to bring them in (a web view is the likely one). Custom CSS card backgrounds stay out for now. |
| 2 | Platforms | Windows and Linux first. Windows is looked at in the real window at every step; Linux is at least type-checked in a container, and run where that can be arranged. macOS comes after and is written blind until then. |
| 3 | New dependencies | Yes, where the crate is well known and well tested. |
| 4 | Stored data | A one-time import from the web client's directory at first run; the two stay separate afterwards. |
| 5 | Memory | **300 MB peak, 150 MB average**, without giving up speed. Pictures are decoded at the size they are drawn and kept on disk, not in memory. |
| 6 | The engine as its own crate | A phased migration: modules move out from behind the Tauri feature as each phase needs them, towards a crate of its own. |

## How each task is done

- One task closes a named set of PARITY.md rows and nothing else.
- The engine side first, then the demo engine, then the view; each with a test. Behaviour that only the real engine has gets a live test against a local server.
- Looked at in the real window on Windows, in a round-avatar theme and a square one, before it is called done.
- The suite and clippy pass; the row is changed in PARITY.md; the README says what is new.
- Nothing is committed unless you ask.

## Phase 0: Groundwork

Nothing here is visible except the defects, and everything after depends on it.

| Step | Work | Why first |
|---|---|---|
| 0.1 | Fix the ten defects listed in PARITY.md. Replace the hover card's three-line glimpse with the full card, as Nebula has it. | They are wrong today and all small. |
| 0.2 | Logs: install a log subscriber with a level and a file (move `logging` out from behind the Tauri feature). | The engine's log output is discarded today, which is one reason last night's disconnect could not be explained from your window. |
| 0.3 | Split the engine boundary by family. `engine.rs` (1,000 lines), `real.rs` (3,700), `demo.rs` (1,400) and `engine_api.rs` (3,000) are each one file; every new call touches all four. Make the trait a set of smaller traits (connection, channels, chat, voice, people, administration, files) with one module per family on each side. | The web client reaches about 200 commands this one does not. Without this every one of them lands in the same four files. |
| 0.4 | View parts the kit lacks: tooltip, toast stack, slider, popover that closes on an outside click without swallowing it, segmented control, tabs, a transition helper. GPUI already offers tooltips, tab stops, animation and several windows; none is used yet. | Half of the small rows are "add a tooltip", "make it a slider", "make it a popover". |
| 0.5 | Keyboard: tab stops on every control in the kit, arrow keys and Enter in menus and lists, a visible focus ring. | Cheap while the kit is small, expensive once every screen is built on it. |
| 0.6 | Translations: every string through one lookup, English only at first, reading the web client's locale files where the wording is shared. | Wrapping strings later means touching every file twice. The other three languages follow in phase 8. |

**Done when:** the defects are gone, a log file is written, the suite still passes with the boundary split, and one existing screen (settings) uses the new parts and can be driven from the keyboard.

## Phase 1: The engine tells the truth

The view cannot draw what it is not told. This phase widens the snapshot, then spends that on the rows it unlocks.

| Step | Engine | View rows it unlocks |
|---|---|---|
| 1.1 | The user's permissions per channel | Menus show only what the server allows, in the channel, user and message menus and the admin entries |
| 1.2 | Self-mute, server mute and suppression apart; priority; whisper or shout context on talking | Separate mute badges, priority badge, "whisper" and "shout" marks, correct mute entries |
| 1.3 | Session state (connecting, connected, lost, why), unread per session, reconnect progress | Rail pips and badges, reconnect banner with Retry and Cancel, session status card, unlimited backoff with a switch |
| 1.4 | Channel facts: restricted, history protocol, position, max users, temporary, description marker | Lock icon, history badge, custom icon, password prompt that appears by itself |
| 1.5 | Conversation facts: first unread id, full pin list with who and when, reaction detail, message source for editing, reply and reaction for direct messages | Unread divider, pinned panel, "who reacted", editing that keeps formatting, direct-message actions |

**Done when:** a user without rights sees no admin entries; the rail shows a server connecting, lost and reconnecting; a restricted channel shows its lock and asks for its password.

## Phase 2: What is seen all day

Small and medium view work that needs nothing new from the engine after phase 1. This is the largest single drop in open rows.

- **Conversation reading:** "new messages" pill, jump to a message with a flash, time once per block, sticky avatar, column capped on wide windows, empty and loading states, message style (bubbles / flat / compact), text size, 12 h and 24 h clock, date formats.
- **Message text:** spoilers, monospace code and code blocks, block quotes, numbered lists, sized headings, tables, shortened link text, selectable text, link warning with trusted hosts.
- **Message actions:** hover pill, "read by" list, picture menu, delete others' messages where allowed, drafts per conversation.
- **Channel list and people:** click the count to join, join that turns voice on, talking bars, a click pinning the card, the user menu from every surface, "join their channel", move-to-channel picker, drag a user onto a channel, per-user volume as a slider and remembered.
- **Rail and connect:** saved servers on the rail, tile menu complete, hover card per server, reordering, quick connect, leave confirmation, favourite star, certificate chooser, search by host.
- **Window:** size and place remembered, follow the system's light or dark, fullscreen, hide the channel column and member panel, in-window keys for mute, deafen, settings, channel up and down.
- **Member panel and friends:** server-wide members by role with search, offline members, right-click; friends as a column, grouped, with unread counts.

**Done when:** the main screen measured against the web UI with `tools/compare.py` deviates no more than it does today (about 0.3 %, the README's last measurement), with the new parts on screen, in two themes.

## Phase 4: The application shell

- Tray with mute, deafen, disconnect, show, quit.
- Global push to talk, mute and deafen; the shortcut recorder and the Shortcuts page; several whisper and shout targets with their own keys (engine: more than one target).
- Notifications on Windows and macOS, a click opening the conversation; taskbar badge and flash; per-channel silence.
- Sounds: the web client's ten events and seven sounds, with the Notifications page.
- Single instance, deep links (`fancy://`), invite links followed and minted, device links.
- Saved passwords in the system's credential store; password and one-time-code dialog with "remember".
- First-run setup; import from the web client's data.
- Updater.

**Done when:** the client can be left in the tray and used from another program: push to talk works there, a mention notifies with a sound, and an invite link opens it.

## Phase 5: Voice

- Engine: the rest of the voice settings (gate open and close, hold, max gain, denoiser choice and tuning, packet size, exclusive mode), a microphone level stream, calibration, microphone test and replay, audio statistics, voice off.
- View: the Voice page as the web has it, with the live meter and draggable thresholds.
- Recording dialog with a remembered folder, file name template and clock.

**Done when:** the voice gate can be calibrated and watched moving, and every option on the web's Voice page exists here.

## Phase 6: Media in the conversation

- Remote pictures behind a "load content" choice, decoded at the size drawn and cached on disk; animated GIFs; several pictures as one tiled block.
- Lightbox: step through the conversation's pictures, zoom and pan, its own menu.
- Link cards as the web draws them: several per message, poster shapes, source, facts, inline play for direct video.
- The attachment tray: files wait, are previewed, go out with the text as one message; share options; upload progress with cancel (engine: batch send, progress, options).
- File cards with open, saved state, expiry; "my shared files" and downloads.
- Full emoji picker with search; server emotes; GIF picker (engine has both, unexposed).
- Mention list with roles; slash commands arrive with plugins in phase 9.
- Voice messages; inline audio and video players.

**Done when:** a conversation with pictures, a GIF, a file batch and three links reads the same in both clients.

## Phase 7: The remaining settings pages

Account (password sign-in, e-mail, two-factor, devices, device linking, recovery phrase), Language & format, Privacy (dual path, streamer mode, embeds), Appearance (wallpaper, server list placement, channel viewer, livery colours), Advanced (logs, reset, reconnect, updates), identities (create by name), "Channels & roles", and the settings search. Each page needs its engine family exposed first; all of them exist in the engine's state today.

**Done when:** every page in the web client's settings nav exists here with every option, or is on the "will not do" list.

## Phase 8: Languages, motion, reach

- German, French and Chinese from the web client's files; language choice; user-authored languages.
- Transitions where the web has them, off under reduced motion.
- The theme details left out so far: glass blur behind header and composer (the renderer can do it now, on Windows), patterned layers, clip paths.
- Blur on Linux and macOS in the GPUI copy.

**Done when:** the client can be switched to German and driven end to end without the pointer.

## Phase 9: Servers that run plugins, and administration

- Plugins on the member side: component trees in messages, modals, slash commands, trust prompt, settings panels, the Plugins page.
- Server branding (livery) shown on the rail, the connect screen and in the theme; the welcome dialog and rich welcome markup; the onboarding questionnaire on joining.
- One administration area, gated: users with roles, roles, bans (add and edit), channel permissions with the tree and groups, the full channel editor, server settings, emotes, invites, server plugins, file server.
- Then the heavy editors, in this order: livery, onboarding, audit log, welcome editor, marketplace.

**Done when:** a server can be set up and run from this client alone.

## Phase 10: The large features

Each is a project of its own and independent of the others, so the order is yours.

| Feature | What it needs that does not exist |
|---|---|
| Screen sharing and camera | The `fancy-screenshare` crate exists. GPUI can only paint video surfaces on macOS; the GPUI copy needs a surface primitive for DirectX and Blade, as the backdrop blur did. Then the picker, the stage, statistics, drawing. |
| Pop-out windows and mini mode | Several windows, which GPUI supports and this client has never used. |
| Watch together | A video player for direct links; YouTube is out (decision 1). |
| Live documents | The engine family, and a collaborative editor, which the composer is not. |
| Calendar and meetings | The engine family; day, week and month views; reminders through phase 4's notifications. |
| Game overlay and rich presence | The `fancy-gamedetect` and `fancy-presence` crates exist; an always-on-top click-through window; Discord bridge. |
| Notepad, forums, friends across servers, account sync | Engine families that exist unexposed. |

## What I would not start with

Screen sharing looks like the most missed feature, and it is the one with the deepest hole under it (a renderer change on two backends). Translations look cheap and touch every file. Both are placed where the ground under them is ready; starting either now would stall on phase 0.
